# 윈도우 입력 시스템 & 훅(Hook) 심층 분석 가이드

이 문서는 윈도우 운영체제에서 키보드 입력이 처리되는 과정과, **훅(Hook)** 기술이 작동하는 원리, 그리고 **유니티 엔진(Unity Engine)**이 개입했을 때 발생하는 현상을 초보자부터 전문가까지 이해할 수 있도록 쉽게 설명합니다.

---

## 1. 윈도우 입력의 여정: "키보드에서 앱까지"

사용자가 키보드를 누르는 순간부터 화면에 글자가 나타나기까지, 입력 신호는 복잡한 여정을 거칩니다.

### 1단계: 하드웨어 인터럽트 (Hardware Interrupt)

* **상황**: 사용자가 'A' 키를 누릅니다.
* **동작**: 키보드 하드웨어가 전기 신호를 컴퓨터로 보냅니다. ("띵! 65번 키 눌렸음!")
* **비유**: 초인종을 누르는 것과 같습니다. 무조건 소리가 납니다.

### 2단계: 시스템 메시지 큐 (System Message Queue)

* **상황**: 운영체제(Windows OS) 커널이 이 신호를 받습니다.
* **동작**: 이 신호를 `WM_KEYDOWN` (키 눌림) 메시지로 포장하여 **시스템 메시지 큐**라는 대기열에 넣습니다.
* **비유**: 우체국에 편지가 도착해서 분류되는 단계입니다.

### 3단계: 스레드 메시지 큐 (Thread Message Queue)

* **상황**: OS는 현재 포커스(Focus)가 활성화된 창(Window)을 찾습니다.
* **동작**: 해당 창을 만든 프로그램(스레드)의 전용 우편함(**스레드 메시지 큐**)으로 메시지를 배달합니다.
* **비유**: "이 편지는 유니티 아파트 101호로 가세요"라며 배달부가 우편함에 넣습니다.

### 4단계: 메시지 루프 (Message Loop)

* **상황**: 응용 프로그램(유니티)은 끊임없이 우편함을 확인합니다. (`GetMessage` / `PeekMessage`)
* **동작**: 메시지를 꺼내서 처리하고(`DispatchMessage`), 화면을 갱신합니다.
* **비유**: 집주인(유니티)이 우편함을 열어 편지를 읽고 "아, A키가 왔구나"라며 행동을 취합니다.

---

## 2. 훅(Hook)이란 무엇인가?: "중간 가로채기"

**훅(Hook)**은 이 여정의 중간 단계에 **'도청 장치'**를 설치하는 기술입니다.

### 개념: 낚시 바늘(Hook)

* 메시지가 최종 목적지(응용 프로그램)에 도달하기 **전**에, 시스템 레벨에서 메시지를 낚아채서 엿보거나 변조할 수 있는 기능입니다.
* **Global Hook**: 시스템 전역에 설치되어, 어떤 프로그램이 포커스 되든 모든 키 입력을 감시합니다. `WH_KEYBOARD_LL` (Low-Level Keyboard Hook)이 대표적입니다.

### 훅 체인(Hook Chain): 줄지어 선 도청자들

* 여러 프로그램이 동시에 훅을 걸 수 있습니다. (예: 카카오톡, Discord, 유니티 등)
* **LIFO (Last-In, First-Out)**: **가장 늦게(최근에)** 설치한 훅이 **가장 먼저** 메시지를 받습니다.
* **규칙**: 내 할 일(로깅)을 마쳤으면, 반드시 `CallNextHookEx` 함수를 호출해 다음 사람에게 메시지를 넘겨줘야 합니다. 이걸 안 하면 먹통이 됩니다.

---

## 3. 유니티 엔진의 개입: "속도광 인터셉터"

유니티(Unity)는 단순한 응용 프로그램이 아니라, **고성능 게임 엔진**입니다. 반응 속도가 생명입니다.

### 일반 앱 (메모장, 웹 브라우저)

* "우체부가 편지(키 메시지)를 줄 때까지 얌전히 기다린다."
* 운영체제의 표준 절차를 철저히 따릅니다. 훅이 정상적으로 동작합니다.

### 유니티 엔진 (게임)

* "우편함 확인할 시간 없어! 내가 직접 우체국 가서 가져올게!"
* **Raw Input / DirectInput**: 유니티는 포커스(Focus)를 얻는 순간, 운영체제의 느린 메시지 전달 과정을 생략하고 **하드웨어 입력 장치(키보드 드라이버)**에 직접 접근하여 데이터를 읽어옵니다.

---

## 4. 왜 "포커스" 때만 먹통이 되는가?

이제 본론입니다. Companion 모드에서 유니티 창을 활성화(포커스)했을 때 훅이 동작하지 않는 이유는 다음과 같습니다.

### 상황 A: 유니티가 '비활성(Background)' 상태일 때 (또는 타 앱 포커스)

1. 사용자가 키를 누릅니다.
2. 포커스된 앱(예: Chrome, Main Mode 등)은 윈도우 메시지를 처리합니다.
3. 윈도우 OS: "자, 전역 훅(Companion) 먼저 보세요."
4. **Companion 훅**: **"오, 키 입력 감지! 로그 남기자!"** (성공) -> 다음으로 전달.
5. 정상 작동합니다.

### 상황 B: 유니티(Companion)가 '활성(Focus)' 상태일 때

1. 사용자가 키를 누릅니다.
2. **유니티(Companion)**: **"내 입력이다! 내가 먼저 처리한다!"**
    * **같은 프로세스** 내의 유니티 엔진이 윈도우 메시지 큐보다 훨씬 앞단계인 **Raw Input** 단계에서 입력을 낚아채서 소비(Consume)해버립니다.
3. **결과**:
    * 유니티가 이미 입력을 처리했으므로, 윈도우 운영체제는 해당 키 이벤트에 대한 `WM_KEYDOWN` 메시지 생성을 생략하거나, 훅 체인 호출 순서를 뒤로 미룹니다.
    * **훅을 설치한 당사자(Companion)**가 스스로 입력을 독점해버려서, 정작 자기 자신이 설치한 훅이 호출될 기회를 잃게 되는 **"팀킬"** 상황이 발생합니다.

---

## 5. 왜 Main Mode는 잘 되는가?

"Main Mode도 유니티인데, Main Mode 포커스 시에는 Companion 훅이 잘 동작함."

### 1단계: 훅 설치 주체 확인

* 코드 확인 결과, **Main Mode는 훅을 설치하지 않습니다.** (`KeyboardModule`은 Companion에서만 생성됨).
* 따라서 **훅 경쟁은 없습니다.**

### 2단계: 프로세스 간 간섭 차이

* **Main Mode 포커스 시**: Main Mode(유니티 A)가 입력을 독점하더라도, 훅을 설치한 것은 **외부 프로세스(Companion B)**입니다. 운영체제는 A의 입력 독점 여부와 상관없이, 전역 훅 체인에 있는 B에게도 메시지를 전달해줍니다.
* **Companion Mode 포커스 시**: 훅을 설치한 **본인(Companion B)**이 입력을 독점합니다. 이때 유니티 엔진(B 내부)이 윈도우 메시지 루프를 우회하거나 차단해버리면, **같은 프로세스에 기생하는 훅(B의 훅)**도 함께 차단당합니다.

## 6. (보존) 해결 시도 기록 및 결과 분석

이 섹션은 문제를 해결하기 위해 시도했던 방법들과 그 결과를 기록합니다.

### 6-1. 방법 1: Input System 설정 변경

* **시도**: `Background Behavior`를 `Ignore Focus`로 설정.
* **결과**: **[실패]**
* **원인**: 유니티 엔진의 Raw Input 사용은 패키지 설정만으로는 완전히 제어되지 않음.

### 6-2. 방법 2: Active Input Handling 변경 (Legacy)

* **시도**: `Both` 모드 확인.
* **결과**: **[실패]**
* **원인**: New Input System과 Old Input Manager가 동시에 활성화되어 내부적인 입력 감지 경쟁이 오히려 심화됨.

### 6-3. 방법 3: 관리자 권한 실행

* **시도**: Companion.exe를 관리자 권한으로 실행.
* **결과**: **[실패]**
* **원인**: 유니티 포커스 시의 입력 독점은 권한(Privilege)의 문제가 아니라, 메시지 펌프 및 Raw Input 소비 방식의 문제이므로 해결되지 않음.

### 6-4. 방법 4: 포커스 시 훅 재설치 (Re-hooking)

* **시도**: `OnApplicationFocus` 시점에 `Unhook` -> `SetHook`으로 훅을 최상단으로 끌어올림.
* **결과**: **[실패]**
* **분석 (Win 키 관련)**:
  * **Win 키**: 이 문제를 발견하기 전부터(처음부터) 입력이 되고 있었음.
  * Re-hooking 덕분이 아니라, **시스템 예약 키(Win)**는 유니티 엔진이 독점/소비(Consume)하지 않고 OS로 흘려보내기 때문에 훅 Chain에 정상 도달했던 것임.
  * **일반 키(A~Z) 불통**: 유니티가 게임 조작 키로 간주하여 **완전히 소비**해버림 -> 훅 체인 도달 전 데이터 소멸.
  * **결론**: 훅의 순서(Priority) 문제가 아니라, **데이터 소멸(Consumption)** 문제임이 명확해짐.

### 6-5. (최종 해결책) 하이브리드 입력 시스템 (Hybrid Input)

* **시도**: "유니티가 키를 먹어서 없애버린다면, 유니티에게 달라고 하면 된다."
* **구현**:
  * **포커스 상태 (Focus)**: `Application.isFocused`일 때, 유니티 내부 API (`UnityEngine.Input.anyKey`)를 사용하여 키 입력 확인. 훅은 무시하거나 Win 키만 처리.
  * **비포커스 상태 (Unfocus)**: 기존 Win32 훅을 사용하여 전역 입력 감지.

## 7. 최종 결론 (Conclusion)

1. **원인 규명**: 유니티 엔진의 **Raw Input 독점** 및 **일반 키 소비(Cancel/Consume)** 특성으로 인해, 같은 프로세스 내의 Win32 Hook (`WH_KEYBOARD_LL`)으로는 일반 키 입력을 감지할 수 없다. (단, 시스템 키는 통과된다.)
2. **해결 전략**: **"싸우지 말고 협력하라" (Embrace Strategy)**
    * 유니티가 입력을 뺏어가면, 뺏긴 후에 유니티에게서 정보를 받아오면 된다.
    * 이원화 전략(Hybrid Input Polling)이 유일하고 확실한 해결책이다.
3. **기여**: 이 분석 과정은 유니티 엔진의 저수준 입력 처리 방식과 윈도우 훅 체인 간의 상호작용을 깊이 이해하는 데 중요한 레퍼런스가 될 것이다.
