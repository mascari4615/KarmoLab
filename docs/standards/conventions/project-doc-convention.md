# 프로젝트 문서화 규칙 (Project Documentation Convention)

Summary: KarmoLab 프로젝트별 문서 구조 및 피처 단위 관리 규칙을 정의하는 가이드라인.

모든 하위 프로젝트(`Apps/*`, `Unity/*`)의 일관된 문서 구조를 유지하여 에이전트와 마스터가 프로젝트 상태를 즉시 파악할 수 있도록 함.

## 1. 기반 폴더 구조 (Project Root Structure)

`Docs/Projects/[ProjectName]/` 경로 내에 다음 파일/폴더를 필수적으로 포함함.

- **`README.md`**: 프로젝트 개요, 기술 스택, 빌드 가이드.
- **`History.md`**: 전역적 주요 마일스톤 및 릴리스 내역 (과거 기록).
- **`Todo.md`**: 현재 진행 중인 작업 및 당장 계획된 태스크 목록 (현재/미래 상태).
- **`Features/`**: 개별 기능(Feature) 단위의 문서들이 위치하는 폴더.

## 2. 피처 단위 관리 (Feature-based Management)

각 피처는 `Features/` 하위에 독립된 폴더로 관리하며, 다음 핵심 문서들을 포함함.

### 2.1. `Spec.md` (명세 및 기획)

- **목적**: "무엇을 만들 것인가?"에 대한 정의.
- **내용**: 기능 요구사항, 사용자 시나리오, API 설계, **검증 계획(Test Case/Play Test)** 등. 구현 에이전트는 마스터가 직접 테스트해볼 수 있도록 구체적인 입력값과 기대 결과(TC)를 명시해야 함.

### 2.2. `History.md` (피처 히스토리)

- **목적**: "무엇이 변했는가?"에 대한 기록.
- **내용**: 날짜별 구현 내역, 결정 사항(Decision Log), 발생했던 문제 및 해결 방법.

### 2.3. `Todo.md` (피처 작업 목록)

- **목적**: "무엇을 해야 하는가?"에 대한 관리.
- **내용**: 현재 남아있는 태스크 리스트, 우선순위, 상호 의존성.

### 2.4. `Result_Report.md` (결과 보고서 / 작업 완료 보고)

- **목적**: "작업 결과가 어떠하며, 어떻게 검증했는가?"에 대한 요약 보고.
- **내용**: 구현된 핵심 기능 요약, **코드 리뷰 셀프 체크리스트**, TC별 테스트 결과(캡쳐/로그 포함 권장), 미흡한 점이나 향후 과제. PM이 코드를 열어보기 전 최종 승인 여부를 결정하는 핵심 근거가 됨.

### 2.5. `Review_Feedback.md` (검토 피드백 / PM 리뷰 결과)

- **목적**: "검토자(PM/메인테이너)가 본 결과는 무엇인가?"에 대한 공식 피드백.
- **내용**: 검토 상태(PASS/FAIL/CONDITIONAL), Critical/Minor Issues 목록, 승인된 항목, 다음 단계 지시사항. 구현 에이전트가 수정 방향을 명확히 파악할 수 있도록 구체적으로 작성함.
- **작성 주체**: PM 또는 메인테이너 (구현 에이전트가 아님!)

## 3. 작성 규칙 (Writing Rules)

1. **명사형 종결**: 다른 모든 문서와 마찬가지로 `~함`, `~임` 스타일을 유지함.
2. **Summary 필수**: 모든 `.md` 파일 상단에 `Summary:` 섹션을 필히 작성함. (H1 헤더 다음 줄에 위치)
3. **Cross-linking**: 관련 있는 피처나 전역 아키텍처 문서(`architecture-overview.md`)를 적극적으로 링크함.
